## 目标
批量生成 50 个可发给试用用户的邀请码，并确认邮箱 / 手机号两种注册登录方式可用。

## 一、生成 50 个邀请码

现状（已查证）：`invite_codes` 表里目前只有 3 个码（FRIEND2026 / FAMILY / EARLYBIRD，均未被使用），注册时由数据库触发器 `on_auth_user_created` 校验邀请码，客户端无法读写该表——机制是正常的。

新增：
- 50 个格式为 `JIMU-XXXX` 的随机码（4 位大写字母+数字，排除易混淆的 0/O/1/I）
- 每个码 `max_uses = 1`（一人一码，便于追踪谁用了哪个）
- 有效期设为 90 天后过期，`note` 标记为「2026 试用批次」
- 通过数据写入工具插入，不改表结构

交付：生成后我会把 50 个码整理成一份清单（同时导出成 CSV 放到可下载目录），你可以直接分发。

## 二、注册 / 登录链路检查

1. **邮箱注册**：确认后台「邮箱确认」开关状态。若开启，用户注册后需先收邮件点链接，而当前 `/auth` 页面注册成功后会直接跳首页 → 会被弹回登录页，体验断裂。处理方式二选一：
   - 关闭邮箱确认（试用阶段推荐，注册即登录，最顺畅）；
   - 保留确认，则修改 `/auth` 提示为「请查收邮箱完成验证」并停留在当前页。
2. **邮箱登录**：验证密码登录、错误提示、邀请码错误的中文提示是否正确。
3. **手机号注册/登录**：检查短信服务是否已配置。目前未接入短信服务商时，「获取验证码」必然失败。若确实没配，我会在手机号 Tab 顶部加一行明确提示「短信登录暂未开放，请使用邮箱注册」，避免试用用户卡在这里。
4. **实际验证**：用一个测试邮箱 + 新邀请码走一遍完整注册流程，确认自动创建了 profile、user_settings，且邀请码 `uses_count` 正确 +1；再用同一个码二次注册，确认被正确拒绝。

## 三、需要你确认的一点
短信（手机号验证码）是否要真正开通？开通需要接入短信服务商（如 Twilio）并提供账号密钥，会产生费用。如果暂时不开通，我就按上面第 3 点做「暂未开放」的友好提示，先靠邮箱 + Google 登录跑试用。

## 技术细节
- 邀请码通过 insert 工具批量写入 `public.invite_codes`，不涉及 schema 变更。
- 邀请码校验逻辑保持在 `public.handle_new_user()` 触发器内，客户端 RLS 仍全面拒绝读写，防止有人枚举邀请码。
- 前端仅可能改动 `src/routes/auth.tsx` 的提示文案。
